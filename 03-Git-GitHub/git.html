01 Mô hình 3 khu vực

Nếu chỉ nhớ được một thứ về Git, nhớ cái này. 90% sự bối rối với Git đến từ việc không biết file của mình đang nằm ở khu vực nào.

Working Directory

Thư mục thật trên ổ đĩa. Sửa file ở đây, Git thấy nhưng chưa ghi nhận gì.

Staging Area (Index)

Vùng đệm bạn tự chọn "cái nào vào commit tới". Đây là thứ Git có mà SVN/Dropbox không có.

Local Repository

Thư mục ẩn .git. Chứa toàn bộ lịch sử — xem log, tạo nhánh đều offline.

Remote

GitHub/GitLab. Chỉ là một bản sao repo đặt trên server, không "thông minh" hơn máy bạn.

Vì sao có Staging Area?

Nó cho phép bạn tách một mớ sửa đổi lộn xộn thành nhiều commit sạch. Ví dụ bạn vừa sửa bug vừa lỡ tay format lại code: git add file-bug.py rồi commit "fix bug", sau đó git add . commit "format". Lịch sử đọc được, revert được từng phần. Ai bỏ qua staging và luôn git add . là đang vứt bỏ tính năng đắt giá nhất của Git.

Bốn trạng thái của một file — git status luôn nói bạn đang ở đâu:

Trạng tháiNghĩa làGit nói gì
untrackedFile mới, Git chưa từng biết đếnUntracked files
modifiedĐã sửa so với commit gần nhất, chưa addChanges not staged for commit
stagedĐã add, đang chờ commitChanges to be committed
committedĐã ghi vào lịch sử, an toànnothing to commit, working tree clean

02 Cài đặt & cấu hình

Làm một lần cho cả sự nghiệp. Nhưng làm sai email thì mọi commit của bạn không được tính vào GitHub profile.

git --version kiểm tra

Khi nào: ngay sau khi cài, để chắc terminal thấy được git.

git --version
# git version 2.45.0  → OK
# Windows: tải tại https://git-scm.com (nhớ chọn cài kèm Git Bash)
# macOS:   brew install git
# Ubuntu:  sudo apt install git

git config --global bắt buộc, một lần

Khi nào: ngay sau khi cài Git, trước commit đầu tiên.

# Tên & email — ký vào MỌI commit của bạn
git config --global user.name "Tran Nhat Minh"
git config --global user.email "nhutminhtran761@gmail.com"

# Editor mặc định khi Git cần bạn gõ text dài
git config --global core.editor "code --wait"

# Nhánh mặc định tên 'main' (chuẩn hiện đại thay cho 'master')
git config --global init.defaultBranch main

# Khi 'git pull' mà lịch sử phân kỳ: mặc định merge (an toàn cho người mới)
git config --global pull.rebase false

# Windows: chuẩn hoá xuống dòng CRLF ↔ LF, tránh diff "cả file đổi"
git config --global core.autocrlf true

# Xem lại tất cả
git config --list --show-origin
Cơ chế

Git đọc config theo 3 tầng, tầng sau đè tầng trước: --system (cả máy) → --global (~/.gitconfig) → --local (.git/config của riêng repo). Vì vậy trong một repo của công ty, bạn có thể git config user.email "..." (không có --global) để dùng email khác mà không ảnh hưởng repo cá nhân.

Bẫy

Email trong commit là văn bản tự do — Git không xác thực gì cả. GitHub chỉ gắn commit vào tài khoản bạn nếu email trùng với email đã đăng ký. Gõ sai một ký tự = commit "mồ côi", không hiện ô xanh contribution.

ssh-keygen nên làm

Khi nào: khi bạn chán gõ token mỗi lần push. Làm một lần cho mỗi máy.

# 1. Tạo khoá (ed25519 = thuật toán hiện đại, ngắn và mạnh)
ssh-keygen -t ed25519 -C "nhutminhtran761@gmail.com"
#    Enter 3 lần để dùng đường dẫn mặc định + không đặt passphrase

# 2. Copy khoá CÔNG KHAI (đuôi .pub — tuyệt đối không đưa file không có .pub)
cat ~/.ssh/id_ed25519.pub

# 3. Dán vào GitHub → Settings → SSH and GPG keys → New SSH key

# 4. Kiểm tra
ssh -T git@github.com
#    "Hi username! You've successfully authenticated..." → xong
An toàn

File id_ed25519 (không có .pub) là khoá riêng — nó chính là danh tính của bạn. Không commit, không gửi cho ai, không đưa lên chat. Lộ khoá riêng = người khác push code dưới tên bạn.

03 Tạo & clone repo

Hai cách duy nhất để có một repo: tự tạo từ thư mục có sẵn, hoặc tải một repo đã tồn tại về.

git init bắt đầu từ số 0

Khi nào: bạn có một thư mục project trên máy và muốn bắt đầu theo dõi nó bằng Git.

mkdir my-project && cd my-project
git init
# Initialized empty Git repository in .../my-project/.git/

# Kiểm tra: thư mục ẩn .git đã xuất hiện
ls -a

Cơ chế: init chỉ tạo thư mục .git chứa objects, refs, config. Xoá .git = project trở lại thành thư mục thường, mất sạch lịch sử (file hiện tại vẫn còn).

git clone tải repo về

Khi nào: bắt đầu làm việc với một repo đã có trên GitHub (của bạn, của nhóm, hoặc mã nguồn mở).

# Qua SSH (khuyến nghị nếu đã cài SSH key)
git clone git@github.com:user/repo.git

# Qua HTTPS
git clone https://github.com/user/repo.git

# Clone vào thư mục tên khác
git clone https://github.com/user/repo.git thu-muc-cua-toi

# Chỉ lấy lịch sử gần nhất — repo khổng lồ tải nhanh hơn nhiều
git clone --depth 1 https://github.com/user/repo.git

# Clone đúng một nhánh
git clone -b develop --single-branch https://github.com/user/repo.git

clone = init + remote add origin + fetch + checkout. Bạn nhận toàn bộ lịch sử, không phải bản snapshot — nên vẫn xem log và tạo nhánh offline được.

.gitignore không phải lệnh — nhưng bắt buộc biết

Khi nào: ngay trước commit đầu tiên. Đây là file quan trọng nhất mà người mới hay bỏ qua.

# Tạo file .gitignore ở gốc repo, ví dụ cho project Python:
__pycache__/
*.py[cod]
.venv/
venv/
.env                # ← BÍ MẬT: API key, mật khẩu DB. KHÔNG BAO GIỜ commit
*.sqlite3
.ipynb_checkpoints/
data/raw/           # dataset nặng — dùng DVC hoặc Git LFS thay vì Git
models/*.pt         # file model hàng trăm MB
.DS_Store
.idea/
.vscode/

# Mẫu sẵn cho mọi ngôn ngữ: https://github.com/github/gitignore
Bẫy chí mạng

.gitignore chỉ có tác dụng với file chưa từng được track. Nếu bạn đã lỡ commit .env rồi mới thêm vào .gitignore, file vẫn nằm trong lịch sử và ai clone cũng đọc được. Xử lý:

# Gỡ khỏi Git nhưng GIỮ file trên máy
git rm --cached .env
git commit -m "Remove .env from tracking"

# Nếu file chứa secret ĐÃ ĐƯỢC PUSH: coi như secret đã lộ.
# Việc đầu tiên là ĐỔI KEY/MẬT KHẨU, sau đó mới nghĩ tới xoá lịch sử.
# Xoá khỏi toàn bộ lịch sử (viết lại history — cẩn thận):
# pip install git-filter-repo
git filter-repo --invert-paths --path .env

04 Vòng lặp hằng ngày

Bốn lệnh này chiếm khoảng 80% thời gian bạn dùng Git. Học thuộc đến mức cơ bắp.

# Vòng lặp chuẩn của một buổi làm việc
git pull                       # 1. lấy code mới nhất của nhóm về
#    ... sửa code ...
git status                     # 2. mình vừa đụng vào những gì?
git add src/auth.py            # 3. chọn cái gì vào commit này
git commit -m "Add JWT login"  # 4. đóng dấu vào lịch sử
git push                       # 5. đẩy lên cho nhóm thấy

git status gõ nhiều nhất

Khi nào: bất cứ lúc nào bạn không chắc chuyện gì đang xảy ra. Không có tác dụng phụ, gõ thoải mái.

git status
git status -s          # dạng ngắn: XY tên-file
#  M  file.py   → đã sửa VÀ đã add (cột 1 = staging)
#   M file.py   → đã sửa, CHƯA add (cột 2 = working dir)
# ?? file.py   → untracked
# A  file.py   → file mới đã add

Đây là lệnh "la bàn". Khi hoang mang, git status luôn nói bạn đang ở nhánh nào, file ở khu vực nào, và gợi ý sẵn lệnh tiếp theo.

git add đưa vào giỏ

Khi nào: khi bạn đã sửa xong một mảng công việc và muốn nó vào commit sắp tới.

git add file.py              # một file
git add src/                 # cả thư mục
git add *.py                 # theo pattern
git add .                    # TẤT CẢ thay đổi từ thư mục hiện tại
git add -A                   # tất cả, kể cả file bị xoá, toàn repo
git add -u                   # chỉ file đã track (bỏ qua file mới)

# ⭐ Vũ khí bí mật: add TỪNG ĐOẠN trong một file
git add -p file.py
#   y = lấy đoạn này · n = bỏ qua · s = chia nhỏ hơn · q = thoát
Nên dùng

git add -p là thứ tách người dùng Git nghiệp dư khỏi chuyên nghiệp. Nó buộc bạn đọc lại từng dòng mình vừa viết trước khi commit — bắt được vô số print() debug bỏ quên và code thừa. Coi như một vòng self code-review miễn phí.

Bẫy

git add . theo phản xạ là cách nhanh nhất để commit nhầm file .env, file 500MB, hoặc code nửa vời của tính năng khác. Luôn git status trước khi commit.

git commit đóng dấu lịch sử

Khi nào: khi bạn hoàn thành một đơn vị thay đổi có nghĩa — không phải theo giờ, mà theo ý tưởng. "Sửa xong bug login" là một commit. "Làm việc buổi chiều" thì không.

git commit -m "Add JWT authentication to login endpoint"

# Commit nhiều dòng: mở editor, dòng 1 = tiêu đề, cách 1 dòng, rồi mô tả
git commit

# Tắt máy nhanh: add mọi file ĐÃ TRACK rồi commit luôn (bỏ qua file mới)
git commit -am "Fix typo in README"

# Sửa commit vừa tạo (quên file / sai chính tả message)
git commit --amend -m "Message mới"
git commit --amend --no-edit    # giữ nguyên message, chỉ thêm file vừa add
Cơ chế

Một commit không lưu "phần khác biệt" — nó lưu snapshot toàn bộ cây thư mục tại thời điểm đó (file không đổi thì trỏ tới object cũ, nên không tốn chỗ). Mỗi commit có: snapshot + tác giả + thời gian + message + con trỏ tới commit cha. Chuỗi con trỏ cha-con đó chính là "lịch sử", và hash SHA-1 của commit được tính từ toàn bộ nội dung đó — nên sửa quá khứ là đổi hash, tức là tạo commit hoàn toàn mới.

Viết commit message tử tế — quy ước Conventional Commits, dùng rộng rãi trong ngành:

<loại>(<phạm vi>): <mô tả ở thì mệnh lệnh, chữ thường, không dấu chấm>

feat(auth): add refresh token rotation
fix(api): handle null user_id in /orders
docs(readme): add setup instructions
refactor(db): extract query builder
test(auth): cover expired token case
chore(deps): bump fastapi to 0.115

❌ "update"  ❌ "fix bug"  ❌ "asdasd"  ❌ "commit lần 3"

Mẹo kiểm tra: message tốt điền được vào câu "Nếu áp dụng commit này, nó sẽ ___". Bạn viết cho chính mình 6 tháng sau, lúc đang truy một bug bằng git log.

05 Đọc lịch sử & so sánh

Giá trị thật của Git không nằm ở việc lưu code, mà ở việc trả lời được: "dòng này ai viết, khi nào, và vì sao?"

git log xem lịch sử

Khi nào: muốn biết chuyện gì đã xảy ra, tìm commit để revert, hoặc lấy mã hash.

git log                              # đầy đủ (q để thoát)
git log --oneline                    # mỗi commit 1 dòng — dùng nhiều nhất
git log --oneline --graph --all      # ⭐ vẽ cây nhánh bằng ASCII
git log -5                           # 5 commit gần nhất
git log --author="Minh"              # lọc theo người
git log --since="2 weeks ago"         # lọc theo thời gian
git log --grep="login"                # tìm trong message
git log -S"calculate_tax"             # tìm commit THÊM/XOÁ chuỗi này (pickaxe)
git log -p file.py                   # lịch sử + diff của riêng 1 file
git log --stat                        # kèm số dòng thêm/xoá mỗi file
Đáng đặt alias

git log -S"tên_hàm" là công cụ điều tra mạnh nhất trong Git: nó tìm đúng commit đã thêm hoặc xoá chuỗi đó, thay vì chỉ tìm trong message. Truy nguồn gốc một dòng code lạ chỉ mất vài giây.

# Tạo alias 'git lg' cho đẹp và gọn
git config --global alias.lg "log --oneline --graph --decorate --all"
git lg

git diff so sánh

Khi nào: trước khi add/commit, để xem chính xác mình đã đổi gì. Bắt buộc trước mỗi Pull Request.

git diff                    # working dir ↔ staging (thứ CHƯA add)
git diff --staged           # staging ↔ commit cuối (thứ SẮP commit)
git diff HEAD               # tất cả thay đổi so với commit cuối
git diff main..feature      # so 2 nhánh
git diff abc123..def456     # so 2 commit
git diff --stat             # chỉ tóm tắt số dòng
git diff -- file.py         # chỉ 1 file

git show · git blame điều tra

Khi nào: show để xem chi tiết một commit. blame khi gặp dòng code khó hiểu và cần biết ai viết, trong commit nào.

git show abc123              # nội dung đầy đủ của 1 commit
git show HEAD               # commit hiện tại
git show HEAD~2             # lùi 2 commit
git show abc123:src/app.py  # nội dung file TẠI commit đó

git blame file.py           # mỗi dòng: hash + tác giả + ngày
git blame -L 40,60 file.py  # chỉ dòng 40-60

Cú pháp trỏ commit: HEAD = hiện tại · HEAD~1 = lùi 1 · HEAD~3 = lùi 3 · abc123 = hash (7 ký tự đầu là đủ) · main@{2} = vị trí nhánh main 2 bước trước.

06 Sửa sai & hoàn tác

Phần quan trọng nhất của trang này. Biết undo là thứ biến Git từ "công cụ đáng sợ" thành "lưới an toàn".

Bạn muốnLệnhMất code không?
Bỏ sửa đổi trong file (chưa add)git restore fileCÓ — vĩnh viễn
Bỏ add (giữ nguyên sửa đổi)git restore --staged fileKhông
Sửa message commit vừa rồigit commit --amendKhông
Xoá commit cuối, giữ code trong staginggit reset --soft HEAD~1Không
Xoá commit cuối, giữ code trong working dirgit reset HEAD~1Không
Xoá commit cuối và xoá luôn codegit reset --hard HEAD~1CÓ
Huỷ một commit ĐÃ pushgit revert abc123Không — an toàn cho nhóm
Xoá file rác chưa trackgit clean -fdCÓ
Lỡ tay reset --hard, cứu lạigit reflog + git reset --hard <hash>Cứu được

git restore hoàn tác ở mức file

Khi nào: bạn thử nghiệm một hướng sửa, thấy sai, muốn quay về nguyên trạng. Hoặc lỡ add nhầm file.

# Vứt bỏ mọi sửa đổi chưa add trong file (KHÔNG UNDO ĐƯỢC)
git restore file.py

# Vứt bỏ toàn bộ sửa đổi chưa add trong repo
git restore .

# Chỉ bỏ khỏi staging, sửa đổi vẫn còn trong file
git restore --staged file.py

# Lấy lại nội dung file từ một commit cũ
git restore --source=HEAD~3 file.py

# (Cú pháp cũ, vẫn gặp nhiều trong tài liệu — làm cùng việc)
git checkout -- file.py
git reset HEAD file.py
Không cứu được

git restore file xoá thay đổi chưa từng được Git ghi nhận — không có reflog nào cứu được, vì Git chưa bao giờ thấy nó. Nếu chưa chắc, dùng git stash thay vì restore: cũng cho working dir sạch, nhưng cất code lại chứ không đốt.

git reset di chuyển con trỏ nhánh

Khi nào: commit rồi mới nhận ra đặt sai chỗ / gộp nhầm / muốn chia lại. Chỉ dùng cho commit CHƯA push.

# --soft : xoá commit, code quay về STAGING (sẵn sàng commit lại)
git reset --soft HEAD~1

# --mixed (mặc định): xoá commit, code quay về WORKING DIR (chưa add)
git reset HEAD~1

# --hard : xoá commit VÀ xoá luôn code. Working dir sạch bong.
git reset --hard HEAD~1

# Gộp 3 commit lộn xộn cuối thành 1 commit sạch
git reset --soft HEAD~3
git commit -m "feat(auth): implement login flow"

# Vứt hết công sức local, đồng bộ y hệt remote
git fetch origin
git reset --hard origin/main
Cơ chế — hiểu cái này là hiểu reset

Nhánh chỉ là một con trỏ tới một commit. reset di chuyển con trỏ đó về commit khác. Ba mức khác nhau ở chỗ nó có kéo theo staging và working dir hay không: --soft chỉ dời con trỏ · --mixed dời con trỏ + xoá staging · --hard dời con trỏ + xoá staging + ghi đè file trên đĩa.

git revert undo an toàn cho nhóm

Khi nào: commit sai đã push lên remote và người khác đã pull về. Đây là lựa chọn ĐÚNG, không phải reset.

# Tạo commit MỚI có nội dung ngược lại commit cũ
git revert abc123

# Revert nhiều commit
git revert abc123 def456

# Revert một merge commit (-m 1 = giữ nhánh chính)
git revert -m 1 abc123

# Revert nhưng chưa commit, để sửa thêm trước
git revert --no-commit abc123
reset hay revert?

Nguyên tắc một câu: chưa push → reset; đã push → revert. reset viết lại lịch sử, nên nếu đồng đội đã pull commit đó về, lịch sử hai bên phân kỳ và họ sẽ gặp lỗi khó hiểu. revert chỉ thêm commit mới — lịch sử vẫn tuyến tính và ai cũng pull bình thường.

git reflog phao cứu sinh

Khi nào: bạn vừa reset --hard nhầm, xoá nhầm nhánh, hoặc rebase hỏng. Đọc kỹ phần này trước khi hoảng.

git reflog
# abc1234 HEAD@{0}: reset: moving to HEAD~3
# def5678 HEAD@{1}: commit: feature quan trọng ← đây rồi!
# 9012abc HEAD@{2}: commit: work in progress

# Quay lại đúng trạng thái đó
git reset --hard def5678

# Hoặc lấy về thành nhánh mới cho an toàn
git branch cuu-ho def5678
Vì sao cứu được?

Git không xoá commit ngay. reflog ghi lại mọi lần HEAD di chuyển trên máy bạn (mặc định giữ ~90 ngày). Commit "mất" thực ra vẫn nằm trong .git, chỉ là không nhánh nào trỏ tới nữa. Miễn là commit đó từng được tạo ra, bạn gần như luôn lấy lại được. Ngoại lệ duy nhất: code chưa bao giờ được commit.

git clean dọn rác

Khi nào: thư mục đầy file build, file tạm, output không track và bạn muốn dọn sạch.

git clean -n        # ⚠️ LUÔN chạy cái này trước: chỉ LIỆT KÊ sẽ xoá gì
git clean -f        # xoá file untracked
git clean -fd       # xoá cả thư mục untracked
git clean -fdx      # xoá cả file bị .gitignore bỏ qua (kể cả .env, .venv!)
Không hồi phục

clean xoá thẳng khỏi ổ đĩa, không vào thùng rác, không có trong Git. -x sẽ nuốt luôn file .env của bạn. Luôn -n trước.

07 Nhánh & merge

Branch trong Git rẻ đến mức gần như miễn phí — nó chỉ là một file 41 byte chứa mã hash. Đó là lý do văn hoá "một nhánh cho mỗi tính năng" trở thành chuẩn.

git branch · git switch tạo & chuyển nhánh

Khi nào: mỗi lần bắt đầu một tính năng mới, một thử nghiệm, hay một bản sửa lỗi. Đừng bao giờ code thẳng trên main.

git branch                       # liệt kê nhánh local (* = đang đứng)
git branch -a                    # kể cả nhánh remote
git branch -v                    # kèm commit cuối của mỗi nhánh

git branch feature/login         # tạo nhánh (nhưng chưa chuyển sang)
git switch feature/login         # chuyển sang
git switch -c feature/login      # ⭐ tạo VÀ chuyển, một lệnh
git switch -                     # quay lại nhánh vừa rời (như 'cd -')

git branch -d feature/login      # xoá nhánh ĐÃ merge (an toàn)
git branch -D feature/login      # xoá ép, kể cả chưa merge
git branch -m ten-moi            # đổi tên nhánh hiện tại

# (checkout là lệnh cũ làm cả hai việc — nay tách thành switch + restore)
git checkout -b feature/login

Quy ước đặt tên phổ biến: feature/ten-tinh-nang · fix/mo-ta-loi · hotfix/su-co-production · chore/cong-viec-vat. Nhất quán giúp cả nhóm đọc danh sách nhánh mà hiểu ngay.

git merge gộp nhánh

Khi nào: tính năng trên nhánh phụ đã xong và được duyệt, giờ đưa về nhánh chính.

# Luôn ĐỨNG TRÊN nhánh nhận, rồi merge nhánh nguồn vào
git switch main
git pull                          # cập nhật main trước đã
git merge feature/login

# Ép tạo commit merge dù có thể fast-forward → giữ dấu vết nhánh
git merge --no-ff feature/login

# Gộp cả nhánh thành ĐÚNG 1 commit trên main (lịch sử main rất sạch)
git merge --squash feature/login
git commit -m "feat: login flow"

# Đổi ý giữa chừng khi đang conflict
git merge --abort

Fast-forward là gì? Nếu từ lúc bạn tách nhánh, main không có commit mới nào, Git chỉ cần đẩy con trỏ main tới trước — không tạo commit merge nào. Gọn, nhưng mất dấu vết là đã từng có một nhánh. Dùng --no-ff khi bạn muốn giữ dấu vết đó cho dễ revert cả tính năng sau này.

08 Xử lý conflict

Conflict không phải lỗi, và không phải dấu hiệu bạn làm sai. Nó chỉ là Git nói: "hai người sửa cùng một dòng, tôi không dám tự quyết".

Quy trình 5 bước bình tĩnh

# 1. Git báo conflict, dừng lại giữa chừng
git merge feature/login
# CONFLICT (content): Merge conflict in src/auth.py

# 2. Xem file nào dính
git status

# 3. Mở file, sửa tay (xem dưới), xoá hết dấu <<< === >>>

# 4. Đánh dấu đã giải quyết
git add src/auth.py

# 5. Hoàn tất
git commit          # message merge được điền sẵn, chỉ cần lưu

# Nếu muốn bỏ cuộc, quay về trước khi merge
git merge --abort

Đọc dấu conflict:

<<<<<<< HEAD
    timeout = 30          ← phiên bản của NHÁNH BẠN ĐANG ĐỨNG
=======
    timeout = 60          ← phiên bản của NHÁNH ĐANG MERGE VÀO
>>>>>>> feature/login

Bạn quyết định: giữ 30, giữ 60, hay viết cái thứ ba (ví dụ timeout = 45).
Sau đó XOÁ SẠCH cả ba dòng dấu <<<, ===, >>>.
Bẫy kinh điển

Quên xoá dòng ======= rồi commit. Code sẽ lỗi cú pháp và cả nhóm nhận được một commit hỏng. Sau khi sửa xong, luôn chạy thử code trước khi git commit, và tìm nhanh bằng grep -rn "<<<<<<<" .

# Công cụ hỗ trợ
git diff                       # xem các đoạn đang conflict
git checkout --ours file.py    # lấy nguyên bản nhánh mình
git checkout --theirs file.py  # lấy nguyên bản nhánh kia
git mergetool                  # mở công cụ 3 cửa sổ (VS Code làm việc này rất tốt)
Phòng bệnh hơn chữa

Conflict lớn gần như luôn là hệ quả của nhánh sống quá lâu. Ba thói quen giảm conflict tới mức gần bằng không: pull main về nhánh mình mỗi ngày, giữ nhánh ngắn (dưới 3 ngày), và chia việc sao cho hai người ít đụng cùng file.

09 Remote: push · pull · fetch

Remote chỉ là một repo Git khác đặt ở nơi khác. Không có phép màu nào ở đây — GitHub không "biết" gì hơn máy bạn.

git remote quản lý kết nối

Khi nào: sau git init muốn nối lên GitHub, hoặc khi đổi URL repo.

git remote -v                    # xem đang nối tới đâu
git remote add origin git@github.com:user/repo.git
git remote set-url origin <url-moi>
git remote remove origin
git remote add upstream https://github.com/goc/repo.git   # repo gốc khi fork

origin chỉ là tên gọi quy ước cho remote chính, không phải từ khoá của Git. Khi fork một dự án mã nguồn mở, quy ước là: origin = bản fork của bạn, upstream = repo gốc.

git push đẩy lên

Khi nào: commit xong và muốn backup lên mây / cho nhóm thấy / mở Pull Request.

git push                              # đẩy nhánh hiện tại (nếu đã có tracking)
git push origin main                  # nói rõ remote và nhánh
git push -u origin feature/login      # ⭐ lần đầu đẩy nhánh mới: -u để nhớ liên kết
git push --tags                       # đẩy tag (không tự đi theo push thường)
git push origin --delete ten-nhanh    # xoá nhánh trên remote

# Ép ghi đè sau khi rebase — CHỈ trên nhánh riêng của bạn
git push --force-with-lease
--force vs --force-with-lease

--force ghi đè remote vô điều kiện — nếu đồng đội vừa push gì đó, code của họ bốc hơi. --force-with-lease kiểm tra trước: nếu remote đã đổi so với lần bạn fetch cuối, nó từ chối. Luôn dùng bản -with-lease. Và tuyệt đối không force lên main/develop.

git fetch vs git pull kéo về

Khi nào: đầu mỗi buổi làm việc, và trước khi tạo nhánh mới. fetch khi muốn xem trước; pull khi muốn nhập luôn.

# fetch: TẢI VỀ nhưng KHÔNG đụng vào code của bạn — an toàn tuyệt đối
git fetch origin
git log HEAD..origin/main --oneline   # xem nhóm đã làm gì trước khi nhập
git diff HEAD origin/main             # xem chi tiết

# pull = fetch + merge (gộp luôn vào nhánh hiện tại)
git pull

# pull kiểu rebase: lịch sử thẳng, không sinh merge commit rác
git pull --rebase
Thói quen tốt

Trong repo lạ hoặc nhánh quan trọng, fetch rồi xem log trước, merge sau. pull gộp hai bước vào một và đó là lúc người ta bị bất ngờ. Với nhánh cá nhân, pull --rebase giữ lịch sử gọn hơn hẳn.

10 Rebase · cherry-pick · stash · tag

Nhóm lệnh "trung cấp". Không bắt buộc cho tuần đầu, nhưng dùng thạo thì lịch sử repo của bạn trông như của người có nghề.

git rebase viết lại lịch sử

Khi nào: nhánh của bạn đã cũ so với main và bạn muốn "dời chân đế" lên đỉnh main, để Pull Request là một đường thẳng sạch sẽ.

# Đứng trên nhánh của mình, dời nó lên đỉnh main
git switch feature/login
git rebase main

# Nếu conflict: sửa file → git add → tiếp tục (KHÔNG commit)
git add file.py
git rebase --continue
git rebase --skip       # bỏ qua commit này
git rebase --abort      # huỷ, trả về nguyên trạng

# ⭐ Rebase tương tác: dọn dẹp 5 commit cuối trước khi mở PR
git rebase -i HEAD~5
#   pick    = giữ nguyên
#   reword  = sửa message
#   squash  = gộp vào commit phía trên (giữ cả 2 message)
#   fixup   = gộp vào commit phía trên (vứt message)
#   drop    = xoá hẳn commit
#   đổi thứ tự dòng = đổi thứ tự commit
Luật vàng của rebase

Không bao giờ rebase nhánh mà người khác đang dùng. Rebase tạo ra commit hash mới cho cùng nội dung; người đã pull nhánh cũ về sẽ thấy lịch sử phân kỳ và rất dễ tạo ra commit trùng lặp khi họ pull. An toàn: chỉ rebase commit chưa push, hoặc nhánh riêng chỉ mình bạn đụng vào.

git stash cất tạm

Khi nào: đang làm dở thì sếp bảo "sửa gấp bug production". Bạn cần working dir sạch để chuyển nhánh, nhưng chưa muốn commit code nửa vời.

git stash                          # cất mọi thay đổi, working dir sạch
git stash push -m "dở phần login"   # cất kèm ghi chú
git stash -u                       # cất cả file untracked

git stash list                     # stash@{0}: On main: dở phần login
git stash show -p stash@{0}        # xem nội dung

git stash pop                      # lấy ra + xoá khỏi kho
git stash apply stash@{1}          # lấy ra nhưng GIỮ trong kho
git stash drop stash@{0}           # xoá 1 stash
git stash clear                    # xoá sạch (cẩn thận)

Stash là ngăn kéo dùng chung cho cả repo, không thuộc nhánh nào — bạn stash ở nhánh A và pop được ở nhánh B. Đừng để stash chất đống nhiều ngày; sau một tuần bạn sẽ không nhớ stash@{3} là gì nữa.

git cherry-pick nhặt một commit

Khi nào: có một commit hay ở nhánh khác và bạn chỉ cần đúng commit đó — ví dụ đưa một hotfix từ develop sang main.

git switch main
git cherry-pick abc123           # chép commit abc123 sang nhánh hiện tại
git cherry-pick abc123 def456    # nhiều commit
git cherry-pick abc123..def456  # một khoảng
git cherry-pick -n abc123       # chép nhưng chưa commit, để sửa thêm

Cảnh báo: cherry-pick tạo commit mới với nội dung giống nhưng hash khác. Nếu sau đó bạn merge cả nhánh nguồn vào, cùng một thay đổi có thể xuất hiện hai lần trong lịch sử.

git tag đánh dấu phiên bản

Khi nào: phát hành một phiên bản (v1.0.0), hoặc đánh dấu một mốc cần quay lại được — ví dụ "kết quả model đạt accuracy 0.94".

git tag                                   # liệt kê
git tag -a v1.0.0 -m "Bản phát hành đầu"   # tag có chú thích (nên dùng)
git tag -a v1.0.0 abc123 -m "..."          # tag một commit cũ
git show v1.0.0
git push origin v1.0.0                    # tag KHÔNG tự push
git push --tags                           # đẩy tất cả tag
git tag -d v1.0.0                         # xoá local
git push origin --delete v1.0.0           # xoá trên remote

Quy ước Semantic Versioning: vMAJOR.MINOR.PATCH — MAJOR khi phá vỡ tương thích, MINOR khi thêm tính năng vẫn tương thích, PATCH khi chỉ sửa lỗi.

11 GitHub & Pull Request

Git là công cụ; GitHub là nơi cộng tác. Pull Request không phải tính năng của Git — nó là phát minh của GitHub, và là nơi phần lớn việc "làm việc nhóm" thật sự diễn ra.

Quy trình đóng góp chuẩn feature branch workflow

# 1. Đồng bộ main
git switch main && git pull

# 2. Tách nhánh cho công việc mới
git switch -c feature/user-profile

# 3. Làm việc, commit nhỏ và thường xuyên
git add -p && git commit -m "feat(profile): add avatar upload"

# 4. Đẩy nhánh lên
git push -u origin feature/user-profile

# 5. Mở PR trên GitHub (hoặc bằng GitHub CLI)
gh pr create --title "Add user profile" --body "Closes #12"

# 6. Sửa theo review → commit tiếp → push (PR tự cập nhật)
git commit -m "fix: validate avatar size" && git push

# 7. Merge xong, dọn dẹp
git switch main && git pull
git branch -d feature/user-profile

Viết Closes #12 trong mô tả PR: khi PR được merge, GitHub tự đóng issue số 12. Các từ khoá dùng được: closes, fixes, resolves.

Fork & đóng góp mã nguồn mở open source

Khi nào: bạn muốn sửa một dự án không có quyền push. Đây cũng là cách xây dựng hồ sơ GitHub gây ấn tượng.

# 1. Bấm Fork trên GitHub → clone BẢN FORK của bạn về
git clone git@github.com:BAN/repo.git && cd repo

# 2. Thêm repo GỐC làm upstream để còn đồng bộ về sau
git remote add upstream https://github.com/GOC/repo.git

# 3. Đồng bộ với repo gốc trước khi làm gì
git fetch upstream
git switch main
git merge upstream/main

# 4. Tách nhánh, làm việc, push lên FORK của bạn, rồi mở PR về repo gốc
git switch -c fix/typo-in-docs

Git Flow được dạy rất nhiều ở trường nhưng ngày càng ít dùng trong thực tế — chính tác giả của nó cũng đã viết ghi chú khuyên cân nhắc trước khi áp dụng. Với dự án cá nhân và hầu hết công ty làm web, GitHub Flow là đủ và nhanh hơn nhiều. Đừng chọn quy trình phức tạp chỉ vì nó trông chuyên nghiệp.

12 Lệnh nâng cao

Không cần cho tuần đầu. Nhưng khi cần thì không gì thay thế được.

git bisect săn bug bằng nhị phân

Khi nào: "hai tuần trước còn chạy, giờ hỏng, mà có 300 commit ở giữa". Bisect tìm ra thủ phạm trong ~8 lần thử.

git bisect start
git bisect bad                  # commit hiện tại: hỏng
git bisect good v1.0.0          # commit này: còn tốt
# Git tự nhảy tới commit giữa → bạn test → trả lời:
git bisect good                 # hoặc: git bisect bad
# ... lặp lại vài lần, Git chỉ đúng commit gây lỗi
git bisect reset                # quay về trạng thái ban đầu

# Tự động hoá hoàn toàn nếu có test
git bisect run pytest tests/test_login.py

300 commit → khoảng 8 lần kiểm tra (log₂300 ≈ 8.2). Đây là ứng dụng thực tế đẹp nhất của binary search mà bạn sẽ gặp — liên hệ thẳng với mảng 02.

git worktree nhiều nhánh cùng lúc

Khi nào: cần mở đồng thời hai nhánh (ví dụ đang train model ở nhánh A, cần sửa gấp bug ở nhánh B) mà không muốn stash.

git worktree add ../hotfix-dir hotfix/loi-login
# Giờ có 2 thư mục, 2 nhánh, dùng chung 1 kho .git
git worktree list
git worktree remove ../hotfix-dir

14 Cấp cứu

Bốn tình huống khiến người mới hoảng loạn nhất. Gần như tất cả đều cứu được.

😱 Tôi lỡ git reset --hard và mất công sức mấy tiếng

Cứu được nếu code đó đã từng được commit.

git reflog                    # tìm dòng commit cuối trước khi reset
git reset --hard HEAD@{1}    # hoặc dùng hash cụ thể

Nếu code chưa từng commit thì Git không có bản sao nào — hy vọng cuối cùng là Local History của VS Code (Ctrl+Shift+P → "Local History").

😱 Tôi commit nhầm vào nhánh main 
# Chưa push: dời commit sang nhánh đúng
git branch feature/dung-cho        # đánh dấu vị trí hiện tại
git reset --hard HEAD~1            # trả main về trước
git switch feature/dung-cho        # commit vẫn còn nguyên ở đây

# Đã push: dùng revert cho an toàn
git revert <hash> && git push
😱 Tôi push nhầm file .env chứa API key lên GitHub
Thứ tự xử lý rất quan trọng

1. Đổi ngay toàn bộ key/mật khẩu đã lộ. Repo public bị bot quét trong vòng vài giây — coi như key đã mất. Xoá lịch sử là bước 2, không phải bước 1.

# 2. Gỡ khỏi tracking + thêm vào .gitignore
git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: stop tracking .env"

# 3. Xoá khỏi TOÀN BỘ lịch sử (viết lại history — báo cả nhóm trước)
# pip install git-filter-repo
git filter-repo --invert-paths --path .env
git push --force-with-lease
😱 Git bảo "Your branch and 'origin/main' have diverged"

Nghĩa là: bạn có commit local mà remote chưa có, và remote có commit mà bạn chưa có. Ba lựa chọn:

# A. Gộp lại (an toàn nhất, sinh 1 merge commit)
git pull

# B. Đặt commit của mình lên trên (lịch sử thẳng, đẹp hơn)
git pull --rebase

# C. Vứt hết công sức local, lấy y hệt remote (KHÔNG hồi phục)
git fetch origin && git reset --hard origin/main
Nguyên tắc cuối cùng

Trước khi chạy bất kỳ lệnh nào bạn không chắc, hãy tạo một nhánh cứu hộ: git branch backup-$(date +%s). Mất 1 giây, và nó biến mọi thao tác nguy hiểm thành có thể quay đầu. Đây là thói quen của người đã từng mất code một lần.
